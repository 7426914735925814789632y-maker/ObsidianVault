---
意味: 全体を統括する管制塔と単一工程を担うSEチャットを分離し、承認ゲート付きセクション計画と創発的マニュアルで開発を進める手法。
---

## 概要・トリガー
- **呼び出しワード / 発火条件:** 機能やフェーズが複数にまたがる開発プロジェクトの進行時
- **対象 / 連携先:** 管制塔チャット（PM / アーキテクト）、SEチャット（担当工程の実装エンジニア）、Obsidian等のマニュアル用MD
- **動作:** 管制塔が工程採番・共通設計図・セクション指示書を発行し、SEチャットが提出したセクション計画を管制塔が承認してから実装・確定へと進める

## 役割の定義
- **管制塔（役割：PM / システムアーキテクト）**
  - 全体の要件定義、工程数とSEチャット数の把握・工程番号の採番、共通全体設計図の作成、各SEチャット向け指示書（思考課題）の発行、セクション計画の承認、および生きたマニュアルの維持を担う。長大な実装コードは書かない。
- **SEチャット（役割：セクション担当エンジニア）**
  - 割り当てられた単一工程について、まず全体計画に沿った「セクション計画書」を作成し、管制塔の承認後に設計・コーディング・デバッグを行う。工程完了後は確定仕様サマリーを出力して役割を終える。

## 仕組みとルール
1. **工程の採番と全体設計図の共有**
  - プロジェクト開始時、管制塔は必要な工程数とSEチャット数を把握してすべてに **工程番号（工程1, 工程2...）** を振る。
  - 全SEチャットへ共通で渡す「共通の全体設計図（コンパクト工程表＋全工程共通の厳守事項）」を単独の ` ```markdown ` コードブロックで出力する。
2. **セクション指示書の作成（思考課題の付与）**
  - 管制塔が各SEチャット向けに出力する指示書では、具体的な実装手順を細かく命令せず、**「達成すべき思考課題」** と **「他工程と接続するための絶対制約（IF境界のみ）」** を提示し、思考容量の分散とSE側の柔軟性を維持する。
3. **承認ゲート付き2段階実行とセクション計画**
  - SEチャットは指示書を受け取ったら、**いきなり実装コードを書かず、はじめに必ず全体計画に対する「セクション計画書（サブ工程・完了条件）」をコピペ可能なコードブロック形式で出力して待機する。**
  - 人間を介して管制塔チャットがセクション計画を把握・**承認**した後に、初めてSEチャットが実装を実行する。
4. **記号による進捗同期とフッター義務**
  - 進捗共有は以下の5記号を用いる：
    - `[TODO]`：未着手 / `[WIP]`：実装・テスト中 / `[BUG]`：エラー発生（スクショ共有） / `[PASS]`：動作確認完了 / `[DONE]`：工程完了・仕様確定
  - **SEチャットは毎回の返答文末に、必ず自身のセクション計画における進捗ポイントの記号をフッターとして付与する。**
    - フッター例：`【工程2 進捗】2-1:[DONE] / 2-2:[WIP] / 2-3:[TODO]`
5. **工程表（ロードマップ）の視認性・コピペ最適化ルール**
  - 工程表はチャット本文に混ぜず、独立した ` ```markdown ` コードブロックで出力する。
  - 横幅の狭い画面で縦折り返しが発生する **Markdownテーブル（`| ... |`）は禁止** し、1工程＝「`[状態]` **工程N：内容**」＋「完了条件（1行）」のコンパクトな箇条書きで1画面に収める。
6. **マニュアルの創発的更新**
  - 各SE工程で確定した仕様・計画変更・解決した思考課題を管制塔側で随時統合し、プロジェクトの「生きたマニュアル（Obsidian等への記録用MD）」を更新し続ける。

## AIが陥りやすい罠・必須の制約事項（仕様の勘所）

「管制塔がコードや細かい手順まで指示するな、思考課題だけ渡してSEに考えさせろ」
1. **管制塔のマイクロマネジメントによる思考負荷集中＝**
  - 管制塔が内部の関数設計や細かい実装手順まで命令すると、管制塔のコンテキストが肥大化し、SEチャット側の柔軟な最適解探求も阻害される。
  - **対策:** 他工程と接続する絶対制約（関数名・シート名等の境界）のみを固定し、それ以外は「何を達成すべきか」という思考課題としてSEチャットへ委任する。

「SEチャットにいきなりコードを書かせるな、まずセクション計画を出させて管制塔で承認しろ」
2. **計画未合意のままの実装暴走＝**
  - SEチャットが全体設計とのズレや認識違いを抱えたまま実装を始めると、後工程で手戻りが発生する。
  - **対策:** SEチャットには初回応答で「コピペ形式のセクション計画書」のみを出力させ、管制塔の承認（計画把握）を得てから実装を開始させる。

「SEの返答は必ず進捗フッターで締めさせろ」
3. **セクション内の現在地ロスト＝**
  - SEチャットと複数回デバッグのやり取りをしていると、セクション計画のどこまで完了したか見失いやすい。
  - **対策:** SEチャットの返答末尾に必ず進捗記号フッター（例：`2-1:[DONE] / 2-2:[WIP]`）を出力させ、スクショやコピペだけで管制塔へ同期できるようにする。

「工程表にMarkdown表を使うな、コードブロック内の箇条書きで1画面に収めろ」
4. **テーブル出力による視認性崩壊とコピペの手間＝**
  - チャット上にMarkdownテーブルで工程表を出すと、列幅が潰れて記号や工程名が縦に折り返され、工程表だけコピペもしにくい。
  - **対策:** 工程表は必ず ` ```markdown ` コードブロック内に独立させ、1工程＝箇条書き2行で出力する。
